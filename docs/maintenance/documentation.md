# 文档维护约定

> 适用于本插件 README、`docs` 及第三方声明。当前状态统一从[文档总导航](../README.md)进入。

## 放在哪里

| 位置 | 保存内容 | 更新方式 |
| --- | --- | --- |
| 根 README | 项目简介、最短开发入口和主要文档链接 | 保持简短，详细状态链接到总导航 |
| `docs/README.md` | 全部主题入口、当前阶段结论与待验范围 | 有状态变化时同时更新依据链接 |
| `quick-start` | 用户和开发者当前可执行的操作 | 同步界面名称、参数、默认行为及排错 |
| `reference` | 当前实现契约、架构边界、SDK 接入及固定上游参考 | 用源码核对；示例能力与已注册能力明确区分 |
| `roadmap` | 尚未实施的后续能力、可选增强与待决方案 | 明确候选范围和依赖，不将已实施设计继续作为待开发清单 |
| `maintenance` | 可反复使用的验证矩阵、当前待验清单、部署 / 发布和文档维护步骤 | 保留操作方法与待验状态；单次执行结果链接到记录 |
| `archive/plans` | 已实施或已被后续设计承接的原方案、决策完成的评估快照 | 标明实现与验收各自状态，链接当前契约和剩余验收，保留原设计 |
| `archive/records` | 带日期的实施、完成度复核、测试、部署和验收记录 | 新操作另建记录，原始证据保留原字节 |

归档按文档用途分类，不等于功能全部完成或验收通过。V5 / V6 原方案与 V6 候选评估已归入 `archive/plans`，当次实施与复核归入 `archive/records`；[待验清单](netease-v5-v6-acceptance.md)继续跟踪性能、实机与用户验收，可选未实施项由路线图承接。方案正文中的旧实施语气与待办只描述当时状态，不作为当前执行指令。

## 如何表达状态

- V 是方案 / 实施编号，M 是能力里程碑，插件包版本以项目配置为准。
- 分别描述代码已接入、自动检查通过、真实 Host 启动、实机交互验收、用户确认和正式发布，并附各自依据。
- 后续实现覆盖旧差项时，在当前导航说明承接关系，在旧记录顶部加后续入口；保留旧表格、测量值和当时结论。
- 截图必须区分 Headless / Skia、Standalone 和真实 Host；离线解码不证明真实声卡出声。
- “最新部署”标明日期并链接对应记录。历史构建次数、测试数量、哈希和清理结果只描述当次操作。
- 上游能力清单和 Workbench / Workflow 接入示例不能作为当前插件已实现能力。

## 迁移与检查

1. 将记录放入对应版本目录，带上操作日期；将其加入[归档索引](../archive/README.md)。
2. 同步所有入站链接，重算迁移文件内的出站相对路径；涉及标题调整时也检查锚点。
3. 更新总导航、README 和当前使用 / 维护说明中的状态入口，避免继续把历史复核当作当前缺项清单。
4. 原始 TRX、JSON、截图与日志不移动、不改写；遵守 `.gitattributes` 中的证据字节保护。确需迁移证据时单独核对摘要。
5. 执行下列检查，并审阅 Git 差异，确认没有混入业务、依赖、生成产物或用户数据变更。

```powershell
. ./tools/DevelopmentChecks.ps1
Assert-MarkdownLinks (Get-Location).Path
git diff --check
git diff --stat
```

链接检查只证明路径和锚点有效；还需人工确认所有文档可从总导航逐层到达、当前说明与源码一致、历史记录的时间和证明范围没有被改变。仅整理文档无需完整业务门禁，更多验证分工见[验证指南](verification.md)。
