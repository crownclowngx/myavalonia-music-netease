# V7 · M3 管理自己的音乐专用实施方案

> 编写日期：2026-09-24。状态：**实施方案已编写，业务代码、V7 门禁与真实账号验收均未实施**。
> 本文承接[能力路线图的 M3](netease-capability-roadmap.md#m3管理自己的音乐)，V7 是方案 / 实施序号，不是插件包版本。开发按本文分阶段执行，测试要求见[V7 专用验证矩阵](../maintenance/netease-v7-m3-music-library-verification-plan.md)。
> 首要约束：SOLID；朴素使用设计模式；新增及修改的关键代码使用详细中文注释，解释设计思路。本轮不使用 AIFLOW、Windows CI 或发布门禁。

## 1. 目标、交付边界与完成标准

用户能够完成“听到喜欢的歌曲 → 标记喜欢 → 收藏别人的歌单 → 创建自己的歌单 → 整理曲目 → 重新打开确认结果”的完整流程。V7 扩展现有播放器，不重新建设登录、队列、歌词、图片缓存或 Dock 接入。

开发约束按以下顺序执行：

1. **SOLID 是首要架构规定。** 网络协议、业务写入、一致性规则、页面状态与控件呈现分别负责自己的变化；不能为了少建文件把它们堆入 `MusicWorkspace` 或 `PlaylistBrowser`。
2. 保持现有 C# + Flurl 直连方式，普通 MVVM、构造注入、端口与适配器、类型化结果和普通事件足够；不增加 Node 服务、通用命令总线、事件溯源、工作流引擎、通用仓储或新的状态管理框架。
3. 写入成功必须有服务端依据，超时不能当作失败后随意重发；远端结果与本地显示状态分别建模。
4. 单元测试、协议测试、生产控件交互测试、门禁自身失败注入和文档检查同步交付，不在功能完成后补一份仅列名的测试清单。
5. 只使用**本地开发门禁**。Windows x64 本机运行测试仍然允许；不新增或运行 Windows CI，不执行发布构建、ZIP 发布、签名、上传、部署门禁。正式发布时再按[发布流程](../maintenance/deployment-and-release.md)执行。
6. 只修改本任务所需文件，保留已有工作区改动；不因 V7 文档存在就更改包版本、伪造测试记录或自动提交、推送、发布。

V7 开发完成要求：所有范围项实现、自动门禁通过、当前契约和使用文档同步。M3 验收完成还要求真实账号写后回查、真实 Host 交互和用户确认。只完成其中一层时按实际层级记录，不勾选整个 M3。V5 / V6 的[既有待验事项](../maintenance/netease-v5-v6-acceptance.md)继续独立跟踪。

## 3. 固定实施范围

| 编号 | 必做能力 | 完成后用户可观察的结果 |
| --- | --- | --- |
| V7-01 | 读取真实喜欢状态 | 搜索、歌单、队列、最近播放和当前播放区对同一歌曲显示一致；未知状态有明确提示 |
| V7-02 | 喜欢 / 取消喜欢 | 一次明确操作只提交一次写请求；回查确认后同步所有入口 |
| V7-03 | 按 ID 打开歌单 | 能打开尚未收藏的歌单，形成新增收藏入口；错误 ID、不可访问有反馈 |
| V7-04 | 收藏 / 取消收藏歌单 | 详情状态与“我的歌单”同步；不能把自有歌单当作可收藏的他人歌单 |
| V7-05 | 创建普通歌单 | 校验名称，成功后以服务端歌单 ID 打开详情，并更新自建列表 |
| V7-06 | 修改名称、修改描述 | 两项分别保存；失败保留对应草稿；显示服务端最终内容 |
| V7-07 | 添加歌曲到自有歌单 | 从歌曲行或当前播放区选择目标；已存在明确提示，不重复插入 |
| V7-08 | 从自有歌单移除歌曲 | 明确歌单和歌曲目标，回查后更新详情及计数，不改变播放队列 |
| V7-09 | 删除自有普通歌单 | 单独确认目标，成功后同步多 Document 导航及列表 |
| V7-10 | 写入一致性、账号隔离与生命周期 | 重复点击、迟到读取、超时、退出、关闭页面和插件不会造成误显示或重复写入 |

本期歌曲增删的必需 UI 为单曲操作；应用层接收有界 ID 集合并处理重复项及部分结果，为端点批量返回保留准确语义。暂不增加跨页多选、批量导入、曲目排序、批量删除歌单、封面上传、私密属性修改、协作歌单编辑、账号资料编辑、推荐发现或云盘管理。

创建固定为普通音乐歌单（`type=NORMAL`、`privacy=0`），表单明确“普通歌单，非私密”；不暗中创建私密歌单。既有私密普通歌单只有在已核对的权限允许时可编辑。创建私密歌单另行扩展，不混入本次范围。

## 4. 页面交互与输入规则

### 4.1 歌曲喜欢与添加入口

- 搜索、歌单、队列、最近播放复用 `SongRowView` 的喜欢呈现与菜单命令；播放条补充当前曲目的喜欢 / 添加到歌单入口。窄布局允许收纳到“更多”，仍能通过键盘到达。
- 初次显示为“喜欢状态待加载”，加载失败显示“喜欢状态不可用，重新读取”。只有权威读取确认后，才能显示“未喜欢”或“已喜欢”；不能用空集合代表读取失败。
- 点击时捕获歌曲 ID 和**明确目标值**，调用 `SetLikedAsync(trackId, desiredValue)`；应用层不提供含糊的远端 Toggle。忙碌时保留原心形并显示正在处理，不先永久翻转再猜回滚。
- 不为每一行发一次 `likelist`。同账号共享一次在途读取和已验证的喜欢集合；刷新、写后回查和重新登录时更新。集合只表达成员关系，不推测喜欢顺序。
- 喜欢变更还会影响内置“我喜欢的音乐”歌单；识别到其真实 ID 后，同步使该歌单详情和目录计数失效并按可见性补读。不能只更新心形而长期留下旧曲目列表，也不能把喜欢集合的无序 ID 当作该歌单的服务端顺序。
- “添加到歌单”弹层列出已核验可编辑的自有普通歌单，支持加载更多；没有目标时提供“创建歌单”。新建成功后停留在已选目标，用户点击“添加”才执行第二次写入，不把创建和添加伪装为原子事务。
- 喜欢不影响可播放资格；无播放地址不自动禁止喜欢。资料缺失但 ID 有效时，先读取所需状态，服务端限制作为独立结果反馈。

### 4.2 收藏歌单与访问入口

- “我的歌单”增加“打开歌单”，接受正整数歌单 ID，使用现有详情读取链路。V7 不解析任意分享网址、不提供全站歌单搜索；这个最小入口用于收藏尚不在列表中的歌单。
- 详情展示收藏状态。自有歌单显示“我的歌单”，他人歌单显示“收藏 / 取消收藏”；权限或收藏状态未知时禁用相应写操作，并提供重新读取。
- 收藏回查确认后标记账号歌单目录失效并刷新；取消收藏后移除已确认的目录成员。不要把用户歌单第一页未找到某 ID 等同于“未收藏”。
- 取消收藏后当前详情若仍可访问则保留，可重新收藏；如访问权随取消而消失，显示不可访问状态并提供返回列表。当前播放继续。

### 4.3 创建与编辑

| 字段 / 操作 | V7 产品规则 | 服务端约束处理 |
| --- | --- | --- |
| 歌单 ID、歌曲 ID | 正整数且能解析为 `long`；拒绝 0、负数、溢出及混入字符 | 不拼接自由 URL，不使用名称充当资源标识 |
| 名称 | 去除首尾空白后 1–100 个 Unicode 标量；拒绝换行及控制字符 | 这是本地上限，不宣称网易上限；A 阶段若确认更严格限制，同步规则、边界测试和本文 |
| 描述 | 允许空字符串用于清空；统一换行为 LF，最多 1,000 个 Unicode 标量；保留正文空格及换行，拒绝 NUL 等非法控制字符 | 字段未读取到与已知空描述分开；未读取到时不允许“保存空白”覆盖原描述 |
| 曲目集合 | 非空、有界，建议每次最多 50 个正 ID；按首次出现去重 | 实际服务端批量限制在 A 阶段核定；超限拒绝，不自动拆成难以追踪的多次写入 |

上述长度属于明确的初始产品预算，使用统一纯规则函数并测试中文、emoji、组合字符、临界长度和粘贴。UI 校验便于提示，应用层仍必须再次校验。

创建成功必须获得有效服务端 ID。不能把本地临时 ID 或同名旧歌单当作新资源。改名与描述分别使用“保存名称”“保存描述”，只提交变化字段，不进行两接口假事务；名称成功但描述失败时保留成功名称和未保存描述，允许单独处理描述。

有未保存草稿时，用户离开编辑区域可选择留在编辑或放弃草稿；Esc 不提交，IME 组合输入期间 Enter 不提交。跨账号或退出时直接撤销并清空草稿，不能把旧账号草稿带入新账号。后台刷新只更新基线，不静默覆盖草稿；保存前若发现基线已改变，提示重新载入或明确覆盖。本地检查无法提供服务端原子并发控制，不宣称跨官方客户端“无冲突”。

### 4.4 移除与删除

- 菜单文案区分“移出播放队列”和“从歌单移除”。后者只在正在浏览的自有普通歌单中提供，确认中展示歌单名称及歌曲名称 / ID。若同 ID 在歌单出现多次，按端点经核定的 ID 语义说明会移除哪些项，不能承诺删除指定位置。
- 删除歌单位于独立危险操作区域，确认展示歌单名称、ID、已知曲目数及“不会清空当前播放队列”。默认焦点放在取消；未知曲目数显示未知，不能当作 0。
- 确认绑定 AccountId、Epoch、目标 ID 和基线版本。点击确认时再次验证，不从当前选中项临时取目标；已变更目标或权限时关闭旧确认并重新读取。
- 内置“我喜欢的音乐”、共享 / 协作或类型未知歌单不开放普通改名、增删曲目和删除。内置喜欢列表只通过喜欢接口维护，不能按名称或列表位置识别内置类型。
- 删除确认成功后，正在看该歌单的 Document 返回“我的歌单”并清理对应编辑草稿；其他 Document 只更新有关条目，不丢掉其他浏览状态。已经加入的队列条目和当前声音保留，不自动删队列或重开媒体。
- 本期远端操作没有撤销按钮；V6 的单步撤销仅作用于本地队列，不能用于恢复远端歌单删除。

所有新增弹层复用现有主题、密度和焦点机制；Esc 先关闭顶层菜单 / 弹层，再处理歌词 / 队列抽屉。确认或错误反馈不能被 150 ms 的视觉加载延迟推迟，按钮忙碌资格立即更新。

## 5. 接口核对与协议边界

沿用[上游清单的固定提交](../reference/netease-api-enhanced-capabilities.md)，本次于 2026-09-24 查看该提交源码。下表是**实现起点，不是接口真实可用的证明**；返回字段、错误码和账号限制由阶段 A 固化，真实可用性由后续实测确认。

| 用途 | 固定上游源码 | 已核对的逻辑端点与参数 | 实施注意事项 |
| --- | --- | --- | --- |
| 喜欢集合 | [likelist.js][up-likelist] | `/api/song/like/get`；`uid` | 模块未显式选协议，不能把无序集合当播放顺序 |
| 设置喜欢 | [like.js][up-like] | `/api/radio/like`；`trackId`、`like`、`alg`、`time`；显式 weapi | 传明确布尔目标；不把喜欢接口业务成功直接当集合已经刷新 |
| 收藏歌单 | [playlist_subscribe.js][up-subscribe] | `/api/playlist/subscribe` / `unsubscribe`；`id`；显式 eapi | 还要求 checkToken v2；上游 `t` 的数值 / 字符串分支存在差异，C# 使用类型化操作并核对有效载荷 |
| 收藏状态补充读取 | [playlist_detail_dynamic.js][up-dynamic] | `/api/playlist/detail/dynamic`；`id`、`n`、`s` | 阶段 A 确认可用的收藏状态字段及缺失语义，不能只根据接口名称假定 DTO |
| 创建 | [playlist_create.js][up-create] | `/api/playlist/create`；`name`、`privacy`、`type`；显式 weapi | 解析真实歌单 ID、名称与类型；响应缺 ID 为未确认结果 |
| 改名 | [playlist_name_update.js][up-name] | `/api/playlist/update/name`；`id`、`name` | 未显式选协议；独立写入、独立回查 |
| 改描述 | [playlist_desc_update.js][up-desc] | `/api/playlist/desc/update`；`id`、`desc` | 未显式选协议；区分空描述与缺失字段 |
| 曲目增删 | [playlist_tracks.js][up-tracks] | `/api/playlist/manipulate/tracks`；`pid`、`op=add/del`、JSON 字符串 `trackIds`、`imme` | 不移植其 code=512 时复制 ID 再发一次的包装分支；逐项回查实际成员关系 |
| 删除 | [playlist_delete.js][up-delete] | `/api/playlist/remove`；JSON 数组字符串 `ids`；显式 weapi | V7 一次只删除一个歌单，确认与回查按同一 ID 执行 |

模块未显式声明协议时，要继续核对 [option.js][up-option] 与 [request.js][up-request] 的配置分支；不能按文件名猜成 GET、weapi 或现有只读协议。原生逻辑端点与 Node 包装路由不同，C# 不调用假设存在的本地 `/like` 服务。

收藏模块的令牌链是已发现的接入差项：当前 `NeteaseRequestEncoder` 没有相应令牌注入。阶段 A 先核对 v2 令牌获取及协议放置位置，再增加仅服务于该端点的最小适配。令牌获取失败时不发送收藏写请求、不返回假成功；不硬编码固定令牌、不偷偷移除要求或换接口重试。若固定实现无法核定，保留明确阻塞记录，M3 不能标记全部完成，其他独立能力仍可开发。

阶段 A 必须产出一份端点契约表：固定源码链接、协议、必要头 / 数据字段、成功及失败响应夹具、权限 / 特殊歌单判断依据、完整性判定、回查接口、服务端限制和尚未实测项。夹具可合成，但必须标明来源，不能把合成数据当线上样本；不保存 Cookie、令牌、原始账号响应或私人歌单内容。

## 6. SOLID 与最小职责划分

### 6.1 建议对象与生命周期

以下是待新增 / 调整的设计名称，不表示文件已经存在。命名可按仓库风格微调，职责边界不可合并回页面大类。

| 层 / 对象 | 负责什么 | 不负责什么 | 寿命 |
| --- | --- | --- | --- |
| `Application/Library/LibraryContracts.cs` | 喜欢状态、歌单元数据、权限、操作意图、写回执、确认结果与快照 | 不含 Flurl、Avalonia 控件、Cookie、URL | 值对象 |
| `ILikedSongsApi` | 读取喜欢集合、按明确目标设置喜欢 | 不控制 UI 或播放 | 无页面状态的适配器 |
| 现有 `IPlaylistCatalogApi` | 保留列表、详情及资料读取，详情补可信 creator / 类型 / 收藏状态 / 完整性；必要的动态读取由适配器内部组合 | 不新增写方法 | 无页面状态的适配器 |
| `IPlaylistMutationApi` | 收藏、创建、名称、描述、曲目增删和删除，返回有类型的写回执 | 不接管整个账号、不刷新页面 | 无页面状态的适配器 |
| `MusicLibraryCoordinator` | 会话资格、当前账号写入串行化、回查、一致快照、失效事件 | 不持有 View、控件或编辑草稿；不拼装 HTTP | 插件容器 Singleton，内部状态按 Epoch 隔离 |
| `LibraryEditRules` | 输入校验、已知权限、差集及部分结果分类的纯函数 | 不访问网络、时钟、磁盘 | 普通静态 / 无状态类 |
| `NeteaseLikedSongsApi` / `NeteasePlaylistMutationApi` | 端点参数、协议选择和响应映射 | 不推断“用户已确认”、不轮询 UI | Singleton，无跨账号可变凭据 |
| `LibraryWriteRequestExecutor` | 复用传输和会话资格，记录是否已进入发送，区分回执、取消及不确定结果 | 不通用自动重试、不替端点解释全部业务码 | Singleton，无页面状态 |
| `PlaylistEditor` | 本 Document 的草稿、目标选择、确认上下文、命令和反馈投影 | 不保存凭据、不直连 HTTP、不拥有播放器 | Scoped / 随 Document 释放 |
| `PlaylistBrowser`、各歌曲区域模型 | 订阅库快照，刷新有关列表、歌曲行和播放条状态 | 不各自维护一份远端写入真相 | 保持既有寿命 |
| View / `SongRowView` | 绑定、焦点、菜单和输入手势 | 不解析协议、不判断所有权、不执行网络 | 随视觉树 |

设计模式只用现有 MVVM、构造注入、边界接口、普通事件订阅。不要为每条命令再造一套接口 / Factory / Strategy；仅在确实需要独立测试外部边界时抽象。`MusicLibraryCoordinator` 按用例组织私有方法，纯规则和协议解析已分离，不再包含大段 UI 映射。

### 6.2 SOLID 的具体审查点

| 原则 | 本期必须满足的检查 |
| --- | --- |
| S 单一职责 | 调整输入长度只动规则及对应测试；改 HTTP 响应只动适配器；改布局不改协调器 |
| O 开闭原则 | 增加一个写端点通过端口和适配器承接，不修改播放、歌词状态机或增加全局协议分支 |

| D 依赖倒置 | 应用层依赖端口、`IMusicSessionAccessor` 和 `TimeProvider`；UI 依赖业务模型；Flurl、JSON 和令牌实现留在 Infrastructure |

## 7. 写入状态、一致性与失败恢复

### 7.1 明确区分回执与确认

共享快照至少包含 AccountId、Epoch、Revision、喜欢集合完整性、已知歌单状态以及当前写操作摘要；不可包含凭据或原始响应。单个状态字段建议使用 `Unknown / Known` 加类型化值，不让 `false` 同时表达未知和未喜欢。

一次操作包含本地 OperationId、账号代次、目标 ID、明确目标值、基线 Revision 和开始时间。OperationId 仅用于本地关联，**不是服务端幂等键**。

| 结果 | 事实 | UI 与后续动作 |
| --- | --- | --- |
| `NotSent` | 本地校验、权限或发送前取消阻止了请求 | 保留状态，修正后可重新发起 |
| `Rejected` | 经端点核定的明确拒绝，能够确认本次未生效 | 保留已确认状态及草稿，显示原因；不是所有非 200 都能直接归入此类 |
| `Confirmed` | 权威回查确认目标状态，或明确确认无需变化 | 更新快照 / 失效通知；区分“本次已修改”和“已经是目标状态” |
| `PartiallyConfirmed` | 集合中部分目标已确认，其余明确未生效或仍未知 | 逐项报告，不用一个成功布尔值吞掉失败 |
| `NeedsRecheck` | 已进入发送，但超时、断网、无效响应或回查仍不能确定 | 保留最近已确认显示并标记待核实，提供“重新读取结果”，不直接显示“重试写入” |
| `StaleSession` | 账号撤销或代次已变 | 丢弃 UI / 凭据 / 快照提交资格；远端可能已执行，重新登录后读真实状态 |

服务端成功回执与回查状态分别保存。若服务端已确认接收，但 Cookie 保存或后续刷新失败，不能把它折叠为可安全重发的失败。传输一旦交接发送而无法证明未发送，即按可能已发送处理。

### 7.2 一次操作的顺序

1. 捕获当前会话、目标和草稿；校验输入及确认上下文，尝试取得当前账号的库写入资格。
2. 读取所需的最新喜欢 / 收藏状态或歌单详情及权限。普通自有歌单要求 creator 匹配、类型已知且相应操作允许；权限未知拒绝写入。客户端检查用于减少误操作，服务端才是最终裁决者。
3. 若目标状态已经成立，返回明确的无变化结果。否则冻结操作意图并再次检查会话资格，发送**一次**写请求。
4. 解析端点回执；对成功或不确定结果走只读回查，写响应不能直接复用“HTTP 200 即成功”的通用逻辑。
5. 回查结束再次核对 AccountId、Epoch、OperationId、Revision；只将有依据的结果合并到共享快照，发布携带身份和受影响 ID 的事件。
6. 页面经 UI 调度器投影事件时再次核对身份、页面寿命、导航代次；最后释放本操作资格。旧操作 `finally` 不能清除新账号 / 新操作的忙碌标记。

### 7.3 采用简单的并发方案

- **V7 每个账号代次最多一个库写操作在途**，预检查、提交和有界回查均属于同一次操作。用一个异步闸门加显式忙碌状态即可；第二次点击返回“正在处理音乐库操作”，不排队、不自动记住反向点击、不等待后再偷偷提交。
- 该资格只约束库写入，不阻塞搜索、播放、定位或只读浏览。不在同步锁中等待网络或投递 UI；短锁只交换快照和操作所有权。
- 未核实结果在有界回查结束后释放闸门，保留相应资源的待核实标记。其他资源仍可编辑；同一资源先重新读取，不允许一键重复创建 / 删除 / 添加。
- 全量喜欢读取与目录读取记录开始时 Revision。写入开始使相关旧读取失效，迟到读取不得覆盖本次确认值；若全量结果跨过一次写入，丢弃后合并一次重新读取，不把旧全量集合覆盖到新状态。
- UI 刷新按受影响歌单 / 歌曲 ID 合并；隐藏 Document 只标记失效，重新显示时补读。单曲操作不引起每行一次请求，也不遍历重建全部控件。
- 其他客户端的改动通过用户刷新、重新登录和每次写入前的最新读取发现；本期不增加后台定时轮询或宣称跨客户端实时同步。界面保留明确刷新入口。

采用账号级串行写是本期低频交互的主动取舍，可直接覆盖多 Document 竞争；暂不引入按资源锁字典、离线任务队列或跨进程事务。

### 7.4 有界回查与不确定结果

只读回查最多 3 轮，首轮立即执行，后两轮分别最多等待 500 ms、1,500 ms；整个自动回查窗口最多 20 秒，包含网络耗时。使用 `TimeProvider` 和可取消等待测试；达到任一预算即停止。429 / 额外验证 / 账号失效立即停止自动回查，显示服务端允许的重试时间或处理入口；不忙循环。

| 写操作 | 权威回查 | 不能作为确认的依据 |
| --- | --- | --- |
| 喜欢 | 同账号完整 `likelist` 的目标成员关系 | 心形已变、旧缓存、失败后空集合 |
| 收藏 | 已核定的详情 / 动态收藏状态；账号目录用于同步列表 | 第一页 / 截断目录找不到歌单 |
| 创建 | 有效回执 ID + 该 ID 的详情、creator 和预期字段 | 同名歌单、创建按钮消失、本地临时 ID |
| 改名 / 描述 | 同 ID 的详情实际字段 | 将请求文本原样写回 UI；忽略服务器规范化 |
| 曲目增删 | 完整曲目 ID 集合中的成员关系；可报告添加前已存在 / 移除前已不存在 | 总数变化、当前 50 行未出现、资料缺失 |
| 删除 | 明确业务回执，加经核定的不存在语义或完整且可核验的账号归属查询 | 单次 403 / 超时 / 普通不可访问、目录第一页未找到 |

服务端最终一致性可能让短时间回查仍旧。预算内未确认不能强判失败，也不能盲目重发。创建若已丢失回执 ID，只能显示“可能已创建，请刷新并核对”，列出的同名新项仅作候选；不自动认领或再次创建。用户核对后明确发起的新建属于新操作，仍不保证远端幂等。

若某端点无法提供可靠回查路径，阶段 A 必须标出，不以本地猜测满足验收。写后确认说明的是读取时的远端状态，不承诺之后不会被官方客户端修改。

### 7.5 曲目部分结果和列表完整性

应用层分别保留输入唯一 ID、执行前成员、回查成员和逐项状态：已添加 / 原已存在 / 已移除 / 原不存在 / 明确拒绝 / 待核实。部分失败只展示真实结果，不通过自动逆向请求“回滚”已成功项。已确认失败项经用户重新选择后才发起新请求，待核实项必须先回查。

当前歌单 `IsComplete=false` 时，不具备证明“不存在”的条件；V7 暂停依赖完整差集的增删操作并说明原因，不私自扩大 10,000 首或 1 MiB 边界。成功后重新读取计数、详情及排序，按 ID 去重合并目录；资料缺失继续占位，不用本地 `Count++` 伪造服务端事实。

喜欢集合建议限制 50,000 个有效 ID，并继续受 1 MiB 传输预算约束；超过预算或结构不完整时整次读取标为不可用，不把未读部分判断为未喜欢。预算常量集中管理，变化须有测试和文档依据。

### 7.6 账号与资源寿命

- 账号退出 / 失效先撤销共享状态的提交资格并取消旧任务，再清空喜欢集合、歌单写状态和草稿。相同 AccountId 重新登录也必须以新 Epoch 隔离。
- 页面关闭只取消该页面草稿和订阅。尚未接受的意图不再发送；已由协调器接受的任务由共享服务完成有界回查，不把页面关闭误报为远端撤销。
- 插件 Shutdown / Standalone 容器释放时拒绝新操作、取消并等待库任务退出，再释放其依赖的登录 / 传输资源；Dispose 可重复调用并等待同一尾任务。保留既有播放停止 / 保存顺序的约束。
- 默认不持久化喜欢状态、编辑草稿或待重放写任务。进程重启后重新读取远端；未确认创建不会在重启后自动重放。账号切换时也不重放。
- 共享服务不引用 View / Document，页面释放订阅；20 次打开、切换和关闭后无残留订阅、轮询计时器或多余媒体打开。

## 8. 中文注释与设计思路要求

新增接口、公共结果、关键状态字段和并发方法使用中文 XML / 行注释。注释说明“为什么这样做、谁拥有状态、什么条件下失效、取消能保证到哪里”，不是逐句复述赋值。参数、取消语义、返回值和例外应在端口契约说明；保留现有英文技术标识，不要求把类型名改成中文。

必注释位置：会话 Epoch 与 CredentialVersion 的区别、操作所有权和 `finally`、发送边界、服务端回执与回查区别、创建无法幂等重试、完整集合要求、系统歌单保护、两字段独立保存、UI 迟到投递和共享 / Scoped 寿命。

```csharp
/// <summary>
/// 将指定歌曲设置为明确的喜欢状态，并通过远端读取确认结果。
/// 设计思路：多个页面共用写入资格和已确认快照，页面不各自翻转本地布尔值。
/// 请求进入发送后，即使超时或用户退出，也不能断言服务端没有执行；此时不得自动重发。
/// </summary>
/// <param name="trackId">有效网易歌曲 ID；调用前和应用层均需校验。</param>
/// <param name="desiredValue">用户本次明确选择的目标值，不依据迟到快照再次取反。</param>
/// <param name="ct">取消等待或尚未发送的工作；不代表撤销已经到达服务端的修改。</param>
/// <returns>已确认、明确拒绝或待核实等类型化结果；成功回执与确认状态分别保留。</returns>
Task<LibraryMutationResult> SetLikedAsync(long trackId, bool desiredValue, CancellationToken ct);
```

这是契约示例，`LibraryMutationResult` 尚未实现。代码评审必须检查注释是否与实际取消及寿命一致，不能用详细注释替代测试。
